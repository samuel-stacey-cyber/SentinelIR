# Literature Review Matrix

This matrix summarises sources relevant to SentinelIR’s research questions. Detailed notes and supporting page references are stored in `reading_notes/`.

For RQ1, compare supported limitations across papers -> explain what they mean for SentinelIR’s design and evaluation. Record these connections in `synthesis.md`.

Status indicates whether a source has only been screened or has been read in sufficient detail to support the entry.

| ID | Theme | Status | Method, Data and Comparison | Main Finding | Strengths and Limitations | Implication for SentinelIR |
| :-: | --- | --- | --- | --- | --- | --- |
| P01 | Alert Investigation Process | `Basically Finished` | Two think-aloud studies investigating what information T1 analysts collected and the actions they took. ES1: five analysts, 200 unique alerts and 400 investigations without AISS. ES2: four different analysts, 18 alerts taken from ES1 and 36 investigations with AISS. Compared the information collected, order of actions and number of actions taken. | With AISS, analysts collected relevance indicators and information about related alerts more consistently. They took fewer actions when investigating alerts classified as Att. There was no significant reduction in actions for NAtt alerts, so the benefit was not the same for every alert type. | Strengths: used practising analysts, reused alert evidence for comparison and checked agreement between transcript coders. Limitations: small participant sample from one SOC; different analysts took part in each study, roughly a year apart; ES2 used fewer alerts. Repeated investigations do not represent additional independent participants. | Mainly relevant to RQ3: useful for thinking about how SentinelIR could organize evidence and guide investigation. Does not establish that guidance improves response-plan quality, so I need to assess that directly. For RQ2, it does not test whether combining access and authentication logs improves detection. |
| P02 | Brute-Force Detection and Evaluation | `Basically Finished` | Flow-based detector using packet-payload histograms + clustering. Validated against access-log labels across 854,945 interactions from a production hosting network. Compared with a previous flow-based approach. | Correctly detected 469 malicious brute-force interactions compared with 237 for the baseline. Normal lookalike and low-intensity attacks remained challenges. | Strength: evaluated production traffic against reference labels. Limitations: labels depend on application-specific assumptions: photo galleries caused false positives; low-intensity attacks could be missed. | RQ1 -> informs normal scenarios and threshold evaluation. RQ2 -> indirect evidence only; does not compare access logs with combined authentication logs. |
| P03 | Access-Log Detection and Evaluation | `Completely Read` | Python rule-based detector using web access logs. Combined normal Jira traffic, crawler traffic, and `DVWA` scans generated using three scanners. Evaluated Type 3 classification at IP-address level; also applied the tool to unlabelled real-system logs. | Reported 99.38% accuracy, 100% precision, 75% recall, and 85.71% F1 -> high accuracy still accompanied by missing positive cases. | Strength: included normal, crawler, and scanner activity. Limitations: different traffic classes came from different environments; unlabelled real-system logs cannot independently establish accuracy; access logs provide incomplete request information. | RQ1 -> informs rule design, controlled data generation, and evaluation limitations. RQ2 -> motivates investigating additional authentication evidence, but does not test the combined-log comparison. RQ3 -> no direct evaluation of response-plan quality. |
| P04 | Event-Linked Response Guidance | `Completely Read` | `Wazuh-based SERC` prototype using retrieval + LLM-generated guidance. Compared GPT-4o and Pixtral 12B responses from simulated attacks against reference responses using cosine similarity + `BERTScore`. | Model performance varied across scenarios and metrics -> output alignment does not establish better user response plans. | Strength: implemented workflow with reference-based comparison. Limitations: similarity scores do not establish technical correctness; no guidance-versus-no-guidance assessment of users’ plans. | RQ1 -> informs guidance design + evaluation limitations. RQ3 -> motivates assessing users’ plans directly. RQ2 -> does not test access-only against combined authentication logs. |
